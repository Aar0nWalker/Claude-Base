# выкати — release to production

Run when the user types `выкати` or `/выкати`.

If this project has no deploy target (a library, a CLI, a local tool), `выкати` means "release"
per [docs/deploy-contract.md](../../docs/deploy-contract.md) — publish/tag — or it means nothing
at all. Say which, once, and don't invent a deployment.

## Steps

1. **Pre-check.** `rtk git status` — the working tree holds the changes to ship and nothing
   foreign. Check `.agents/wip.md` for another agent's active rows. Note the branch.
   A deploy that ships the working copy must refuse a dirty tree — that refusal means someone
   has work in flight, not that you need an override.

2. **Release — start it so you don't block.** The gate plus the deploy take minutes; waiting on
   them wastes those minutes.
   ```bash
   bash scripts/ops/deploy.sh          # run in background — never pipe through `| tail`
   tail -f deploy.run.log | grep -E --line-buffered "gate green|gate failed|\[ERROR\]|complete"
   ```
   - The verdict is the `gate green` line, not the exit code of a wrapped command.
   - Do other useful work between log events; re-check progress every ~5 minutes. No progress
     for two checks in a row → treat it as hung, find what it is stuck on, kill and restart.
   - **Red gate = no release.** Fix the cause and rerun. A failing test is a reason to stop, not
     to bypass. Never assume "just a flake" — prove it.
   - Skipping the gate or narrowing its zone is **not yours to decide**. Only the user may
     authorize it, in that same message, for that one release. Tooling being unavailable is a
     blocker to report, not grounds to ship unverified.

3. **Health check, from outside.** Hit the real entry point and read the logs of what you just
   restarted. If the deploy keeps the previous process alive (blue/green, rolling), make sure you
   are querying the NEW one — the old slot will happily report itself healthy.

4. **Fix errors.** Root cause, minimal fix, re-release, re-check. Repeat until clean. If a bad
   build is already live and no quick fix exists, roll back first and debug after.

5. **Commit + push — only if checks pass.**
   ```bash
   rtk git add <explicit paths> && rtk git commit -m "<what changed>" && rtk git push
   ```
   - **Never `git add -A` / `git add .`** — shared working tree (AGENTS.md → Parallel Work §2).
     Check `git status` first, leave another agent's WIP out, and say that you did.
   - Do **not** commit or push if any check still fails; report the blocker instead.

## Notes

- Secrets never go into commits, logs, or chat.
- Batch: ship several edits from one request in ONE release at the end, not one per edit. Risky
  changes (auth, payments, schema) get their own release so a rollback doesn't drag the rest.
