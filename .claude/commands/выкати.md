# выкати — deploy to production

Run when the user types `выкати` or `/выкати`.

## Steps

1. **Pre-check.** `rtk git status` — confirm the working tree has the changes to ship. Note the current branch.

2. **Deploy.** From the project root:
   ```bash
   bash deploy.sh
   ```
   - Runs backend pytest in Docker locally, rsyncs `frontend/` + `backend/` + root files to the server (`DEPLOY_SSH`/`DEPLOY_PATH` from `.env`), then SSH-runs `start.sh --rebuild` (rolling rebuild of `api`, `worker-fast`, `web`). Output is teed to `deploy.log`.
   - Preview first if unsure: `DRY_RUN=1 bash deploy.sh` (uploads/rebuild skipped).
   - If local Docker pytest is unavailable/blocking: `SKIP_LOCAL_DOCKER_TESTS=1 bash deploy.sh` (only when explicitly needed — tests are a safety gate).

3. **Health + logs.** After rebuild:
   - Site up: `rtk curl -sS -o /dev/null -w '%{http_code}' https://{{DOMAIN}}`
   - API health: `rtk curl -sS https://{{DOMAIN}}/health`
   - Server logs (SSH alias/target = `DEPLOY_SSH` or `DEPLOY_WINSCP_SITE` from `.env`, path = `DEPLOY_PATH`):
     ```bash
     ssh "$DEPLOY_SSH" "cd '$DEPLOY_PATH' && docker compose ps && docker compose logs --tail=200 api worker-fast web"
     ```
   - Also skim local `deploy.log` for build/migration errors.

4. **Fix errors.** If health or logs show errors: find root cause, apply the minimal fix, redeploy (step 2), re-check (step 3). Repeat until clean. If a bad build already reached the server and a quick fix isn't available, `bash rollback.sh` switches back to the previous known-good images (db/redis/storage untouched).

5. **Commit + push — only if checks pass.** When the site is healthy and logs are error-free:
   ```bash
   rtk git add -A && rtk git commit -m "<what changed>" && rtk git push
   ```
   - If not on the main branch, that's fine — push the current branch.
   - Do **not** commit/push if any check still fails; report the blocker instead.

## Notes

- Secrets (`.env`, cookies, SSH keys) never go into commits, logs, or chat.
- `deploy.sh`/`rollback.sh` need `.env` with `DEPLOY_PATH` + `DEPLOY_SSH` (or `DEPLOY_WINSCP_SITE` as ssh-config Host alias).
- If working in a multi-agent shared tree, follow the parallel-work protocol in `AGENTS.md` before deploying: check `.agents/wip.md` and `git status` for another agent's uncommitted work — do not ship it half-done.
